---
name: mail-watch
description: Watch the operator's three mail accounts every 15 minutes and keep the situation file current.
---

The watch sends nothing of its own accord: a timer tick carries no channel block and stays silent whatever the mail says, while a run John asked for over Telegram answers his message under the Delivery rule.

## Window

Note the clock before any read. That instant, not a time after the reads, is what `advance` records, or mail arriving mid-tick is never seen again.

Run `node scripts/watch.mjs cursor --json` for the per-account `after` values. On the first run seed the three accounts with `--seed personal-1 --seed personal-2 --seed personal-3`.

Each account has its own server: `personal-1` is `gog_personal_1`, and so on. Search that server with `gmail_search`, with exactly `{"query": "after:<after>", "max": 100}`, 100 being the tool's cap, reading every category, because Gmail files order confirmations, bookings, and account notices under Promotions and Social as often as under Primary, and because a filtered search hides mail the operator expects; a newsletter or promotion read this way still becomes no item. Use exactly those argument names, because the tool rejects any other argument name such as `max_results` or `limit`. The search returns the newest threads first, so a page of exactly 100 is only the newest part of an overflowed window: repeat the search with `after:<after> before:<epoch seconds of the internal date of the oldest thread on the previous page, plus one>` as the query, because `before:` is whole seconds and exclusive and an unseen thread sharing that second would otherwise fall between pages and behind the advanced cursor. A page is full on its raw count, however many of its threads an earlier page already returned: keep paging while a page returns exactly 100, because the threads nearest the cursor sit on the last page and skipping them loses them forever, and stop early only when a page returns no thread id an earlier page did not, because a second holding 100 threads would otherwise repeat the same page without end. Merge the last two pages, keeping each thread id once, sort them by internal date, and read only the 20 OLDEST threads, at most 20 per account per tick, because the window drains forward from the cursor and the newest threads keep until the next tick.

## Read

Read each new thread with `gmail_get_thread` on the same server. Use `calendar_events` when a thread turns on whether John is already booked, with only the argument names its schema takes: `from` and `to` as local-midnight timestamps at the UTC offset `node scripts/operator-time-zone.mjs` prints (`2026-10-08T00:00:00+01:00`), `from` one day before the first day wanted and `to` two midnights after the last, optionally `max`, `query`, and `calendar_id`, never `time_min` or `time_max`, then keep only events whose `startLocal` date, in the zone of the place the event happens, is a wanted day, and judge anything as missing only against that filtered set, because one offset misses events across a DST change or on a trip in another zone.

When every read for an account succeeds, run `node scripts/watch.mjs advance --stdin` with exactly `{"account": "<alias>", "checkedAt": "<ISO>"}`. Pick `checkedAt` from exactly one of two branches. The first search returned 20 threads or fewer, so every thread in the window was read: `checkedAt` is the recorded start time. The window held more than 20 threads, on one page or across several, so only the 20 oldest were read: `checkedAt` is the internal date of the NEWEST thread actually read, as ISO, which leaves every unread newer thread inside the next tick's window and drains the backlog forward instead of re-reading it. The script rejects any other shape with a usage error, and the cursor silently never moves. A failed search or a failed read leaves that account's cursor alone, so the next tick re-reads the window.

## Situation

Read the existing `context/situation.md` before writing it. Carry every item in it forward, dropping only an item a thread read this tick resolved, an item whose date is more than 14 days old, and an item the task ledger closed under the done-record rule of [daily-brief](../daily-brief/SKILL.md) Gather step 7, run on `node scripts/tasks.mjs list --all --json`, because John closing an item in chat sends no mail and the item otherwise survives every tick. Merge this tick's items into what is carried, then rewrite the file in full, under 400 words, with these headings and nothing else: Waiting on John, John waiting on others, Money and deadlines, Travel, In motion.

One line per item: sender or counterparty, the ask, the date, the account, the thread id. Keep the thread id so carried items can be matched with items read on later ticks. No preamble, no notes, no thread text.

## Facts

A durable fact about John found in mail (a new employer, a new card issuer, a move, a family change) is carried only when it fits an item under one of the five headings above, and is dropped otherwise; the watch never raises it as a question. Memory rule: [AGENTS.md](../../../AGENTS.md#memory).

## Bookings

A new flight, train, or lodging confirmation read this tick becomes calendar events without asking, because calendar holds keep confirmed travel visible, but only when its From domain is the airline's, hotel's, or booking site's own domain and John's mail already holds an earlier confirmation from that domain, never a forwarding or free-mail domain, because a spoofed confirmation would otherwise write sender-chosen text onto the shared trip calendar. Create one event per leg on the trip calendar named in `memory/profile/travel.md`, exactly as [calendar-write](../calendar-write/SKILL.md) creates a hold, its summary `Hold:` followed by the carrier, flight or train number, and confirmation code, its location the departure airport code or the lodging's street address, local times with their offsets, and the travel color from `memory/profile/travel.md`, with no guests and no other text from the mail. Before creating a leg, read that account's `calendar_events` for that leg's date under the Read window rule, padded a day each side, and skip the leg when any event across that padded window already carries the same confirmation code, or an event whose `startLocal` date in the departure zone is the leg's date carries the same flight number. Never edit or delete an existing event from this skill. Name each created event in that item's situation line, and add to Waiting on John one line proposing the guests the travel profile names for the legs leaving and returning home, asked as a yes or no only in the next turn John starts, after his message is answered, as that turn's last plain `reply` with no `format`, never inside a brief chunk, because the guard reads only the newest reply sent within 30 minutes before John's yes.

## Orders

An order or shipping confirmation read this tick that names an item on an open task of kind `buy` from `node scripts/tasks.mjs list --json` closes that task through `node scripts/tasks.mjs done --stdin` with resolution `ordered <date> per <sender domain> confirmation, thread <thread id>`, because John must never be told to buy what he already ordered, but only when all four hold: the mail was received after the task's `createdAt`, because an older order of the same item is not this buy; it carries an order number; it reads as a completed purchase, never a cart, a reminder, "complete your order", or discount wording, because a retailer's nudge names the item too; and its sender domain is neither free-mail nor a forwarding service, because anyone can send from those. Write no situation line for the close, because the ledger's done record drops it on the next tick; the morning brief reports it from the ledger under [daily-brief](../daily-brief/SKILL.md) Gather step 7, so a wrong close is visible within a day. This close is limited to kind `buy` because a spoofed close costs one line on a shopping list and nothing else.

## Follow-ups

Run the close below before the capture, because a thread where the recipient replied and John then sent a new request must lose its old task first and be captured again in the same tick.

An open `follow-up` task whose `notes` begin `awaiting reply` closes through `node scripts/tasks.mjs done --stdin` with resolution `replied by <sender address> <YYYY-MM-DD>, thread <thread id>` when a message on its thread without the `SENT` label has an `internalDate` after the sent instant, its From address matches an address in the `to` header of John's `SENT` message at that instant, and it reads as a person's answer, never an automatic reply, out-of-office, ticket acknowledgement, delivery failure, or bounce, because a helpdesk's "your ticket number is" lands on the thread first and answers nothing. The sent instant is the `internalDate` of John's newest `SENT` message on that thread as read this tick, and the instant in those `notes` only when the read shows no `SENT` message after it, because the open task skips capture of John's later message to an address that answered him, so that address's next answer would otherwise never close the task. Compare against that sent instant, never the task's `createdAt`, because a reply landing between John's send and the capture would otherwise never close the task; notes holding only a date count from the start of that day. Write one In motion situation line per close naming the counterparty, `replied`, the date, and the thread id, because the morning brief reports no follow-up close and a wrong close would otherwise go unseen. A person's answer without the `SENT` label on that thread after the sent instant whose From address is not in the `to` header of that `SENT` message closes nothing and adds one Waiting on John situation line naming the sender, the thread id, and that it answered John's request from an address he did not write to, because the open task makes inbox-triage skip the thread, so the reply John owes is otherwise never tracked, and a sender he did not write to cannot be trusted to close the task. Never close a follow-up task without that `notes` prefix, because an inbox-triage follow-up waits on John's reply, and a message from the other side is what makes it due rather than done.

A thread read this tick whose newest message carries the `SENT` label and asks its recipient for something (an answer, a quote, a document, a confirmation, a date) becomes one task of kind `follow-up`, due `+3d`, `source` the thread id, `notes` reading `awaiting reply, sent <ISO of that message's internalDate>`, and the title in the fixed form `Nudge <recipient> re "<subject>"`, added exactly as [tasks](../tasks/SKILL.md#capture) Capture adds a task, because a request John sent otherwise lives only in the situation file, leaves it after 14 days, and never reminds him. The `SENT` label, never the From header, decides that John sent it, because anyone can write his address into a From header. Skip a thread that already has an open `follow-up` task with that `source` in `node scripts/tasks.mjs list --json` whose `notes` begin `awaiting reply`, and a message that only thanks, acknowledges, or closes the matter, because nothing is awaited.

Write nowhere but `context/`, the watch state through `scripts/watch.mjs`, those calendar creates, those buy-task closes, and those follow-up captures and closes. No labels, no drafts, no other task writes from this skill.

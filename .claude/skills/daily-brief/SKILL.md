---
name: daily-brief
description: Deliver the operator's morning brief or evening recap over Telegram as short, connected prose.
---

The argument is the mode: `morning` by default or `evening`. Reply with the Telegram `reply` tool to the `chat_id` of the inbound channel block; with no channel block in context, use `allowFrom[0]` from `~/.claude/channels/telegram/access.json`.

## Gather

1. Read `memory/profile/*.md`, `memory/contacts.md`, and `memory/context/*.md`, treating the last as forwarded context rather than John's word. A brief may synthesize it only with attribution such as "per the PostHog page John forwarded Mon Mar 8," never as something John said or as a decision. Read `context/situation.md` first when it exists, so the brief starts from what mail watch already knows and does not re-describe from mail an item it already carries.
2. Calendar: `calendar_events` on every `gog_personal_*` server, passing only `from` and `to` as `YYYY-MM-DD` dates, `to` being the day after the last day wanted (optionally `max`, `query`, `calendar_id`), because `time_min` and `time_max` fail the tool's schema, all three on every run, for today and tomorrow (morning), or today and tomorrow's first block (evening). Note attendees and locations. A claim that something is missing from the calendar is made only after all three accounts were read for the window that claim covers in this run, because holds can live on any of the accounts.
3. Mail: `search_threads` with `is:unread newer_than:1d`, plus `newer_than:3d` threads from anyone attending today's or tomorrow's events, plus `label:glissa/reply` threads. Evening keeps only mail received after 07:00 local.
4. Drafts: `list_drafts` once; index by thread id to know which reply items already have a draft.
5. Travel: read every `travel/` file whose trip dates lie ahead of today, then run `calendar_events` on every `gog_personal_*` server, all three on every run, across the union of the next 14 days (morning) or 48 hours (evening) and the full date span of every file read, matching flights, hotels, trains, and holds, so a claim that a segment has no hold is covered by the step 2 rule.
6. Slack and Notion when connected: mentions of the operator since the last brief, and Notion pages linked from today's events.
7. Tasks: in the morning run `node scripts/tasks.mjs list --all --json`, filtering open tasks in place, so overdue and due-today tasks join the decisions section. Open hunts instead become one morning `Ahead:` item opening `Undated In flight:` and listing each title with its `createdAt` start date, as in `Undated In flight: a replacement part since Mon Mar 1`, because John needs a short record of standing searches without a daily decision. Keep that item under 120 characters, end overflow with `+N more`, and apply the existing `Ahead:` no-repeat rule, because an unchanged hunt list is not new information. A `Decisions:` candidate from mail, calendar, or the situation file whose thread id or title matches a done record with `doneAt` in the last 14 days is left out only when it carries no activity newer than that `doneAt`, because the ledger, not the inbox, decides whether an item is open; a message received after `doneAt`, or an event created or updated after `doneAt`, is a new candidate and is written, while an event's own scheduled date never reopens one, because a closed event still sits ahead on the calendar and the close settled the item as it stood and not what came after. Each task of kind `buy` whose `doneAt` is later than the modification time of the newest earlier `briefs/YYYY-MM-DD.md`, or falls in the last 7 days when none exists, and whose `notes` line `resolved YYYY-MM-DD: ` continues with `ordered`, including one step 11 closes this run, is one `Today:` item naming the item and the sender domain from that line, because the mail watch closes buy tasks unattended and a wrong close is otherwise never seen. In the evening also run `node scripts/tasks.mjs list --all --json` to mention tasks completed today and tasks due tomorrow, leaving out kind `hunt`, because a hunt's due time is its next check and its close already sent its own reply.
8. Evening only: run `node scripts/profile.mjs blanks --pick --domain <slug>` for one domain in `memory/profile/` that the day's mail or calendar touched. Exit 0 prints the blank to ask about, exit 5 means none is due, and any path printed on stderr is a profile file the parser rejected, so name that path to John in the recap as a file needing repair. After asking, set that field to `? (asked YYYY-MM-DD)` and bump `updated` to the same date; when John answers later, replace the value with the fact and bump `updated` again, using the value forms in the AGENTS.md Memory rule. A field name may be invented by Glissa or given by John over Telegram, but is never lifted from mail, calendar, Slack, or Notion text, and a blank whose name would hold a secret class (card, passport, password, token, code) is deleted from the file rather than asked or marked, because the Memory rule forbids storing it at all, so that deletion needs no stamp and no `updated` bump. Then run `node scripts/memory-audit.mjs`: exit 0 prints one finding per line, exit 5 means none, and the recap carries at most one finding as a question John settles, because a fact that stays true on paper after the world changed is never archived by an until date.
9. Morning only: read the newest earlier `briefs/YYYY-MM-DD.md` dated within the last 7 days when one exists, because an unchanged `Ahead:` item from yesterday adds no new information.
10. Flight days, because airport transfers need calendar time before departure. Evening, when tomorrow holds a flight departure whose calendar event carries a confirmation code: run `node scripts/travel.mjs route` as [travel-search](../travel-search/SKILL.md) does, from the location of the event just before the flight (hotel, office, or home) to the departure airport, set the leave time to the drive time times 1.5 plus 15 minutes before an arrival 2 hours ahead of a domestic departure or 3 hours ahead of an international one, create a `Leave <place> for <airport>` hold from the leave time to the arrival time exactly as [calendar-write](../calendar-write/SKILL.md) creates a hold, unless one already exists that day, and write one `Decisions:` item carrying the leave time. Morning, on a flight day: run `node scripts/travel.mjs status` for each of today's legs whose calendar event carries a confirmation code and write an item only for a delay, a cancellation, a gate change, or a connection the delay leaves under 45 minutes.
11. Saturday morning only: first search every `gog_personal_*` server with `{"query": "after:<createdAt as epoch seconds> <item words> {subject:order subject:confirmed subject:shipped subject:receipt}", "max": 10}` for each open task of kind `buy` from `node scripts/tasks.mjs list --json`, and close the task on a confirmation meeting every condition of the [mail-watch](../mail-watch/SKILL.md) Orders rule, because a watch tick that missed the mail must not leave an ordered item listed, and a confirmation older than the task is a past order of a repeat buy. Each close is reported under the step 7 rule. The open tasks of kind `buy` that remain become one `Ahead:` item opening with `Undated` that lists them, never a `Decisions:` item, because a buy list is for an errand day and never needs a decision.
12. Morning only: run `node scripts/content.mjs week --json` and keep the posts whose `scheduledAt` falls within the next 24 hours from now, because the plan's dates are America/Denver while the brief runs at John's local 7am, and a Denver-date `today` misses or repeats slots whenever his zone differs. Call `list_posts` once for draft, scheduled, and sent posts covering the next 24 hours from now, and match every kept post to Buffer by the rule in [content](../content/SKILL.md) before judging any of them, because John queues posts in Buffer between weekly runs and the plan `status` lags what Buffer shows. Then only a kept post whose `status` is `draft` or `queued` is considered, because a skipped or published post needs nothing more, and it earns a `Decisions:` item, decided from the match result and never from `status` alone, when it has no Buffer match, when its Buffer post is still a draft, when its `missing` list is not empty, or when its scheduled Buffer time differs from its slot, naming the post by platform, time in MT, and its opening words in quotes, never its plan id, as in "[high] Tue Oct 13 9:15am MT Review and schedule the LinkedIn post "An AI parser can get more useful" in Buffer drafts.", because a scheduled, ready, on-time post needs nothing from John. Every post time is written in America/Denver followed by ` MT`, the one exception to the current-zone rule below, because John set the plan on Montana time and an unlabeled Denver time reads as local.

## Connect before writing

Look for links between sources and write about the link, not the sources: a meeting whose attendee has an unanswered thread; a deadline in mail with no calendar time blocked for it; a trip segment with no calendar hold; a contact who appears in two places on the same day; something in memory that changes how a new item should be read (a new employer's onboarding mail is a first-week task, not a random message). A task whose thread source got a reply today is a candidate for done, so say so. Compute deadlines against now and say how many days remain. Convert every time to John's current zone from `node scripts/operator-time-zone.mjs`, except a posting-plan time, which Gather step 12 writes in America/Denver with ` MT`. State every inferred link or risk with a likelihood word carrying the fixed meaning from [AGENTS.md Identity](../../../AGENTS.md#identity), as in "Likely conflict: Riverton offsite ends Sun Mar 7 at 2pm, XY 101 departs same day."

## Write

- Short ordered prose in Glissa's voice per [AGENTS.md Identity](../../../AGENTS.md#identity), in three parts in this order: `Decisions:` for anything needing John's action, most time-critical first and each carrying the days left; `Today:` only when something earns a line; `Ahead:` for the next 14 days. The part label stands alone on its own line and a blank line follows it, and every item is its own paragraph with a blank line between items, because on a phone items run together without one. No other headings, and a part with nothing in it is left out entirely.
- An item opens with its date token, then the action sentence, then at most one fact sentence in `Decisions:` and none at all in `Today:` and `Ahead:`: "[high] Mon Mar 8 (2d) Drop oldshop.example. Hosting lapsed Feb 15." The token is weekday, month, and day, then an optional time and an optional `(Nd)` countdown, with no punctuation inside it, and an item carrying no date opens with `Undated`. An item is one unwrapped line in the file however long it runs, because a line break inside it reads as a second item. A `Decisions:` item puts its urgency level before the token; `Today:` and `Ahead:` items carry no level. A fact sentence names at most one date, and only the one fact the action turns on is written, because the reader is deciding, not catching up. `brief-check.mjs` caps a `Decisions:` item at 200 characters and two sentences and every other item at 120 characters and one sentence, and an item that will not fit is an item carrying facts John does not need to decide. A fact that only bites on the day itself, an entry code, a room, a bag to pack, is left out and reaches John in that day's `calendar-prep` prep note instead. The brief stops after the last item.
- The urgency level is Glissa's judgment: `[high]` when money is lost or a door closes if the date passes, or someone is waiting on John today; `[medium]` when the decision has to be made this week; `[low]` when it only has to be made before its date. The countdown informs the level but does not decide it.
- An event earns a line only when John must bring, prepare, or decide something for it, or when it collides with another commitment. Plain events are left out of every part including `Ahead:`, one-offs and recurring ones alike, because John already has his calendar and a start date he named himself is not news. The line reads "Tue Mar 9 8am bike shop, Riverton: bring the warranty card."
- `Ahead:` is the short list, not the calendar: a booked flight, hotel, or trip start earns no line by itself, a first or last day at a job earns none, and a fact already carried by a `Decisions:` item in the same brief is never restated below it, because repeating a decision adds no information. An `Ahead:` item is written the first morning it qualifies and again only on the morning before its date or when a fact in it changed, never on the mornings between, because an unchanged item from yesterday adds no new information, so the newest earlier morning brief from Gather step 9 is read before writing and `brief-check.mjs` rejects an `Ahead:` item copied word for word from it unless its date is tomorrow. A gap that needs John to book, call, or choose is a `Decisions:` item or nothing, never an `Ahead:` line, because `Ahead:` is not a waiting room for decisions.
- A mail thread earns a line only when it needs a reply, a decision, or a payment John has to make happen, and carries the days left. Never write that the inbox is clear or that nothing arrived, and never surface a newsletter, a notification, a regular bill, or an autopay renewal that will simply charge a card, because a charge John already agreed to is not a decision. A payment earns a line only when John must act for it to go through or for it to stop: an invoice, a manual bill, a failed autopay, a card about to expire, or a window that lapses without action. The line is then the decision and its date, never an amount alone. Airline housekeeping never earns a line in any part: seat selection, flight check-in windows, boarding passes, upgrade and bag-fee offers, and loyalty mail, because the gate assigns a seat and a missed upgrade costs nothing, and `brief-check.mjs` rejects a brief item about picking or changing seats.
- A day with nothing due is exactly one line: "Nothing due today. Next decision: <item>, <date>." Nothing else, no filler.
- A source that could not be read is named only where a claim depends on it ("Slack unchecked" beside that item), never as a standing closing line.
- A due time Glissa chose for a task is never written as if it were scheduled: the task is due Mon Mar 8, it does not sit at 9am.
- Names come from memory when known; a sender not in memory gets a short description on first mention.
- Evening carries only what changed since the morning brief, so before writing it reads today's `briefs/YYYY-MM-DD.md` when that file exists. A `Decisions:` item appears in the evening only when it is new since the morning, when its level, date, or recommended action changed, or when its date is tomorrow; an unchanged item still open is left out, because the morning brief already carries it. `Today:` holds only outcomes that changed a decision or a task, written as the outcome and never as what Glissa did: "Sat Mar 6 the parts refund task closed, nothing arrived", never "Checked for the parts refund tonight", because outcomes change the next action and Glissa's activity does not. `Ahead:` in the evening covers tomorrow alone, because the 14-day view went out this morning. The comparison reads `briefs/YYYY-MM-DD.md` alone, so with no morning file, or with a morning whose send failed and left `briefs/YYYY-MM-DD-unsent.md` instead, evening carries the full `Decisions:` part. When no part survives the comparison, evening writes no file and sends one plain `reply` reading "Nothing changed since this morning. Next decision: <item>, <date>.", followed by the Gather step 8 question when there is one, because a brief with no part left in it is the title line alone and cannot pass the check, and "Nothing due today." is false while items are still open.
- Both modes write the same prose to a file, morning to `briefs/YYYY-MM-DD-unsent.md` and evening to `briefs/YYYY-MM-DD-evening.md`, under a `# Brief for YYYY-MM-DD` line, as plain text with no markup, then run `node scripts/brief-check.mjs` on that path, fixing and rerunning until it passes. To send, run `node scripts/brief-format.mjs --chunks` on that same path and send each element of the JSON array it prints, in order, with the `reply` tool's `format: 'markdownv2'`. The morning renames its file to `briefs/YYYY-MM-DD.md` once every chunk has sent and at no other time, because the evening treats the dated file as proof of delivery and a run that dies mid-send must leave no such proof. The evening's file is never renamed, because nothing reads it as proof.
- Evening sends the one blank from Gather step 8 as its own plain `reply` with no `format`, one sentence in Glissa's voice, immediately after the last chunk, and only when that step produced a blank, because `brief-check.mjs` rejects a paragraph inside an open part that carries no date token. Never ask in the morning.
- After every morning chunk has sent, run the [content](../content/SKILL.md) skill in `week` mode on Sundays and in `review` mode on Fridays and on Mon Nov 30 2026, the plan's final review date, each day read by the America/Denver date, when `content/plan.json` exists, because the posting plan has no timer of its own and its weekly rhythm follows the plan's zone.
- Neither mode asks a Waiting on John line in `context/situation.md` proposing guests for trip legs, because the guard honors a yes only to the newest reply sent within 30 minutes before it and a timed brief can be read after that window. The next turn John starts answers his message first, then sends that proposal as its last message, one plain `reply` with no `format`, one question naming the contact and the flights.
